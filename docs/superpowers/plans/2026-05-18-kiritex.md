# KiriTeX Maintenance Plan

This plan is organized by module, not by historical date. Future agents should read the design spec first, then use the relevant section below.

## Ground Rules

- Preserve the `KiriTeX` mixed-case logo.
- In the TeX suffix, keep the visual height relation `T > X > E`.
- Use KazeTeX history as background evidence only. Keep useful visual lessons such as logo/title alignment, formula watermarks, robust commands, and Pad TOC navigation; do not restore old KazeTeX command names.
- Do not manually add sequence numbers to titles, problem bodies, choice text, headers, TOC entries, or cover metadata. KiriTeX counters generate those labels.
- KiriTeX 1.0 problem environments are `problem`, `problemtf`, and `problemchoice`; do not add legacy aliases.
- Subparts under a problem use `problemsubparts` with `(1)`, `(2)`, etc. and no special indentation.
- Fill-in blanks use `\problemblock`; sentence-final blanks use `\problemblock*`.
- Keep user-facing documentation organized by feature area: writing rules, problem types, layout, cover, answers, files, maintenance log.
- Compile both demos after changing `.cls` or `.sty` files.

## Module: Class Entry (`kiritex.cls`)

Responsibilities:

- Parse the `pad` option.
- Load `ctexart` with the default compact size.
- Set Latin Modern as the western text family.
- Load required packages.
- Define shared colors before loading internal style files.
- Set paragraph spacing and activate `kiriheadings` at begin document.

Current typography policy:

- A4 default: `zihao=5`.
- Pad mode: bump to `\zihao{-4}` at begin document.
- Western fonts: Latin Modern Roman, Latin Modern Sans, Latin Modern Mono.

## Module: Problem Environments (`kiritex-env.sty`)

Responsibilities:

- Own the shared `problem` counter.
- Reset problem numbering by `section`.
- Render `problem`, `problemtf`, and `problemchoice`.
- Provide `problemsubparts` for subparts under one problem.
- Provide `\problemblock` for fixed-length fill-in blanks.
- Auto-render choice labels A-H and adaptive option layout.

Required behavior:

- Problem prefix is generated once as `题 \theproblem`.
- Users provide semantic content only.
- Pad mode clears the page after every problem-like environment.
- Choice content must not include manual `A.`, `B.`, etc.
- True/false and choice problems must not append automatic parentheses, blanks, or rules.
- Choice prompts must not end with any period, question mark, or other closing punctuation.
- Choice layout is width-based for every supported option count: four, two, or one option per row.
- Subparts must use English parentheses, e.g. `(1)` and `(2)`, aligned at the left edge.
- `\problemblock` renders `\underline{\quad\quad\quad\quad\quad\quad}`; `\problemblock*` appends an un-underlined `。`.

When editing this file, check for accidental duplicate numbering in demo output.

## Module: Page Style and Logo (`kiritex-pagestyle.sty`)

Responsibilities:

- Define `\KiriTeX`.
- Set A4 and Pad geometry.
- Define page headers and footers.
- Generate the cover with `\maketitle`.
- Style links, table of contents anchor, sections, and subsections.

Logo rule:

```latex
\KiriTeX
```

must visually read as `KiriTeX`. The suffix relation is `T > X > E`: raised `T`, normal `X`, lowered small `E`.

Cover rule:

- Use `\title`, `\author`, and `\date`.
- Do not manually duplicate section/problem counts unless the metadata truly needs a human-readable range.
- Keep A4 and Pad covers visually related.

## Module: README

README should remain the user-facing guide. Its section order should be:

1. Project purpose and modes.
2. Quick start.
3. Writing rules, especially no duplicate numbering.
4. Problem types.
5. Layout.
6. Cover.
7. Answers.
8. File structure.
9. Maintenance notes.
10. Dependencies.

Avoid turning README into a chronological changelog. Dated version history belongs in `CHANGELOG.md`.

## Module: Changelog

`CHANGELOG.md` is the only dated release-history document.

It should record:

- behavior changes in class/style files;
- documentation reorganizations that affect future agents;
- demo content updates that clarify supported syntax;
- important lessons imported from sibling projects.

Do not duplicate the full changelog inside README or design specs.

## Module: Design Spec

The design spec is the source of truth for future agents. Keep it concise and normative.

It must include:

- non-negotiable numbering policy;
- logo casing and `T > X > E` rule;
- mode differences;
- problem environment contracts;
- cover contracts;
- verification commands.

## Verification Checklist

Run after style/class changes:

```bash
xelatex -interaction=nonstopmode demo-a4.tex
xelatex -interaction=nonstopmode demo-a4.tex
xelatex -interaction=nonstopmode demo-pad.tex
xelatex -interaction=nonstopmode demo-pad.tex
```

Then scan logs for real errors or warnings:

```powershell
Select-String -Path demo-a4.log,demo-pad.log -Pattern '^!|LaTeX Warning|Package .* Warning|Error|Font .*not found'
```

Expected:

- PDFs are generated.
- No LaTeX errors.
- No missing Latin Modern font messages.
- `\KiriTeX` reads as mixed-case `KiriTeX`.
- No title/problem/choice duplicate numbering.
